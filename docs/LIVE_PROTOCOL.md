# Live protocol reference

Broker uses the OpenAI Node SDK's `LiveWS` and `ClientEvent`/`ServerEvent` types. GPT-Live carries the conversation; Primary Dexter is the account-bound backend. The implementation is in `src/live/session.ts` and `src/broker/server.ts`.

| Path | Contract and implementation rule |
| --- | --- |
| Audio | `session.output_audio.delta` carries base64 `delta`. The primary WebSocket supplies no `event_id` or audio-done event. Preserve identical chunks and assign local playback delivery IDs. |
| Transcripts | Input/output transcript deltas carry `event_id`, `delta`, `start_ms`, and `end_ms`. Keep snapshots in delivery order. They are observations, written off the media path (`BrokerStore.observeTranscript`); a journal write never waits in the audio path for a transcript fragment. Fragments can arrive after speech; wait for acoustic and transcript settling before submitting the complete request. |
| Delegation | `session.delegation.created` supplies `delegation.id`, `target`, and `offset_ms`; build task text from saved transcripts. Broker requests client mode and accepts omitted/null delegation in the returned session. Every update about a task carries its `delegation_id`. Quiet progress uses `session.thinking.append`, and only when something useful changed. A confirmed final result uses `session.commentary.append`, outcome first, as soon as it is saved. GPT-Live chooses where the result fits in its own speech. A caller who is mid-sentence holds the result for up to 2 s. A generation that must be replaced to admit the result still waits for a pause. Progress for a task that already has its final result is dropped (`live.update.outdated`). Each request to Primary carries the speech of the 90 s before it, at most six turns (`voiceContext.recentSpeech`, `src/broker/conversationContext.ts`). When Dexter told the caller account facts earlier in the call that this window no longer holds, the first item is one compact `dexter` block of them: "Earlier on this call, the voice already told the caller: …" (`src/broker/toldFacts.ts`). Those facts are Dexter's own sentences that state an amount, describe the portfolio or a holding, name a holding from a portfolio note, or report an outcome. Questions and progress talk are not facts. The block repeats nothing still in the window and uses at most 2000 of the 6000 characters, with five turns of recent speech after it. Facts sharing words with the request come first, then the newest. In call 1325b55e the caller asked about a token Dexter had said they held, a minute after the portfolio read-out had left the window, and Primary answered that it had never mentioned the token.

  - A cancelled request is spoken outcome first, keeping any step that already settled (a confirmed sale).
  - A final result whose delivery was rejected, unconfirmed or closed is re-sent up to three times. When any part of the earlier delivery may have been heard (an unconfirmed chunk, or chunks accepted before a later one failed), on this voice session or on one since replaced, quiet context first tells the voice: "If you already told them, refer back to it briefly; if not, give it as news." A delivery that was rejected outright, never heard, is re-sent plainly. After that the caller hears "I couldn't pass on the result of that request. Please check the Dexter app for it."
  - If the journal cannot be written and tracking stops, the caller hears "I can't track that request right now. Please check the Dexter app for its result." That notice is spoken on the current voice without the journal. |
| Task list | The application owns the caller's task list on each call (`src/broker/voiceTasks.ts`). It is sent as quiet context (`session.thinking.append`, `delegation_id: null`) whenever a task changes: one header and one line per task, each line within one 500-token append. The newest list replaces every earlier one. Statuses are in progress, waiting to start, waiting for the caller's answer, finished, failed, cancelled, and not started. A finished task states its result only after that result has been delivered to the voice. The instructions make the list the only truth about requests. |
| Guardrail | Monitor-and-correct, per [voice server controls](https://developers.openai.com/api/docs/guides/voice-server-controls#apply-conversation-guardrails) (`src/broker/voiceGuardrail.ts`). Every assistant sentence is judged against the application's task list by the Decisions API (`gpt-6-luna`, 2.5 s timeout, about 150 ms). It runs off the audio path. The judge also sees results not yet delivered to the voice and delegations not yet admitted. If the list changes while the judge runs, the sentence is judged again, up to three rounds. The last verdict is kept, never dropped. A clear contradiction gets an application-authored `session.instructions.append` correction tied to the task's delegation. Clear means contradiction ≥ 0.98, a false success, a false failure or a step never started, and no match with any listed result. The correction asks the voice to say it misspoke and lists the tasks, the one the claim refers to first. A contradiction that also matches a listed status or result is ambiguous: a finished sale beside an open cancel, say. It gets a neutral restatement of the voice's own task list instead, with each request's status and delivered result. So does an outcome or money claim the judge cannot answer: a judge call that returns nothing is retried after 300 ms and 900 ms first. A restatement never says "you misspoke" or "you don't have the result", so nothing true is retracted. A no-verdict restatement with the same content, in any task order, is never sent twice, and no-verdict restatements are limited to one per 20 s, because each append can cut into Dexter's speech. A detected contradiction, ambiguous included, is a real false claim, and only the 4 s cooldown applies to it. The judge also gets what Dexter already told the caller earlier in the call: its own account-fact sentences, the same kind Primary gets, minus any the guardrail found false. It is asked whether the latest sentence denies or contradicts them. If it does (≥ 0.98), as when the voice relays "I haven't mentioned Maple" after reading Maple out, the voice gets a neutral restatement quoting its own earlier words, the related one first. It asks the voice to say plainly if the two conflict, never to deny having said it, and to offer to check. A sentence with no earlier statements gets the calibrated judge request unchanged. Corrections carry statuses, delivered results and Dexter's own earlier words only, never caller words. Only a correction the voice accepted starts the 4 s cooldown. A correction blocked only by one still awaiting its acknowledgement is held, not dropped. The latest is kept, but a restatement never displaces a clear correction. If the earlier one is refused or times out, the held one goes out, judged again first if the task list changed meanwhile. If it is accepted, the held one stays suppressed. Every failed judge call is logged with its status, `Date` header and body (`broker_voice_guardrail_judge_failed`). The guardrail never touches audio, playback or the call. Each trigger is logged (`broker_voice_guardrail`) and kept on the call (`voiceGuardrail`, last 50). Offline replay of 551 cached real verdicts: the correction rule says "misspoke" to no true sentence at 0.98. It catches 6 of 31 labelled false claims, every cancel-era false claim among them. The misses are mostly stale "still on it" lines. |
| Appends | Send `event_id`; correlate `*.appended` through `client_event_id` and rejections through `error.client_event_id`. The SDK can deliver one protocol error through both callbacks: deduplicate it and preserve recoverable command rejection. |
| Close | Send `session.close`, await matching `session.closed` and usage, then drain transcript persistence. Track audio playback separately from provider finalization. Each provider session's real close reason and provider error code is logged (`broker_voice_closed`) and kept on the call (`voiceCloses`, last 20; unknown provider codes are stored as `unrecognized_provider_code`). The call's own end reason is `endReason` (`broker_call_ended`). No safety feature ends, mutes or stalls a call. A call ends when the caller hangs up, at the call deadline, or when a connection it depends on fails, and the caller hears which:
  - A Live session that drops or reports a provider error not tied to a command (a 429 included) ends the call with "My voice connection stopped working" (`voice_unavailable`).
  - A Dexter API failure (eligible context or admission reads) ends it with "I lost the connection to your Dexter account" (`account_unavailable`), never blamed on the voice. The rest of the sentence is built from the call's requests (`accountUnavailableSpeech`):
    - work already sent to the account keeps running;
    - work queued behind another, or never sent, won't run;
    - an unanswered question is waiting;
    - a result not yet given is in the Dexter app.
  - A stalled carrier media socket ends it with "I lost the audio on this call" (`media_socket_stalled`).
  - Reconnecting a dropped Live session within the call is not built yet. |

See the official [WebSocket event contract](https://developers.openai.com/api/docs/guides/voice-websockets#send-and-receive-events) and [client delegation guide](https://developers.openai.com/api/docs/guides/live-delegation#keep-the-conversation-context-in-your-application).

Keep input flowing throughout startup and silence: 160 bytes of 8 kHz PCMU every 20 ms. Put conversation policy in `instructions` and account reference data in initial history. After `session.started`, send the explicit opening through `session.instructions.append` with `delegation_id: null`. Its receipt confirms acceptance; audio and playback establish the greeting. Follow the official [opening sequence](https://developers.openai.com/api/docs/guides/live-conversations#greet-before-the-caller-speaks).

Account calls usually open with a pre-rendered greeting clip that the broker plays on the Twilio stream before Live exists. The opening then tells Live the caller already heard it (`brokerOpening(..., greeted)`): inbound Live waits for the caller, and outbound Live continues with the offer. Caller audio spoken over the clip never reaches Live; an attached Live receives silence of the same length. Audio after the clip is held until Live attaches and is sent first, in order. Live output that arrives while the clip plays is held behind it. An outbound opening makes Live speak first, so caller speech held while Live started is delivered before it, and the opening (`brokerOpening(..., greeted, heardCaller)`) tells Live the person may have answered: it acknowledges briefly and offers in the same reply. Held silence does not delay the opening. See [BROKER_OPERATIONS.md](BROKER_OPERATIONS.md#greeting-and-media-start).

SDK-typed fixtures in `tests/live-session.test.ts` participate in normal `npm run typecheck`. Run them with `node --import tsx --test tests/live-session.test.ts`.

`scripts/qualify-live-phone.mts` accepts `--module-root`, `--module-variant src|dist`, a new `--evidence-dir` outside the repository, and `--config-file`. Optional `--input-audio` takes raw 8 kHz PCMU; use the neutral request "Please ask Primary for my test phrase."

Qualification uses actual Live preflight/audio/transcripts with simulated Twilio callbacks, playback receipts, and Primary. The dummy result is "Your test phrase is blue lantern." Check greeting before caller speech, complete submitted request, spoken result, and finalization. This exercises the SDK and broker media path without a telephone carrier or a real account.

`evals/` is a bench for the delegation protocol against real `gpt-live-1`. It runs through the broker's real server, generation, and Live session code, with only Twilio and the Dexter API faked. Seven scripted scenarios use TTS caller audio (`evals/scenarios.ts`). `evals/run.ts` runs N calls per scenario against any `--module-root`, so a previous release can be the baseline. `evals/score.ts` applies deterministic checks plus a `gpt-6.1-sol` judge over each timeline: false or contradicting claims (and whether they were corrected), phantom tasks, promised steps, false corrections, answers to unrelated chat, results reported, and latency. `evals/guardrail-calibrate.ts` replays scored sentences through the guardrail judge offline, to measure caught claims against false corrections for each threshold. Each script's header gives its command. Spend: Live is $0.05 per minute; a seven-scenario pass is about $0.30. Run benches with their own OpenAI key (`--config-file` pointing at an eval env file), never production's, so an eval can't drain the key calls depend on. `evals/guardrail-calibrate.ts --offline 1` replays cached judge verdicts only and makes no API call.
